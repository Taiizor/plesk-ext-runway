# Runway — foundation notes (Phase 2)

What Phase 2 built, how the pieces fit together, and what the Phase 3 agents (3a helper,
3b PHP, 3c frontend, 3d repo hygiene) must know. This is a Phase 2 snapshot: statements about
missing features (sample, fetch, path/worker modes, customer access) are outdated, see
[DESIGN.md](DESIGN.md) and [INTEGRATION-REPORT.md](INTEGRATION-REPORT.md). [DESIGN.md](DESIGN.md) stays the source of
truth for decisions and contracts; this file documents the implementation.

## 2. Frontend build with Bun

- `bun install` installs `@plesk/plesk-ext-sdk@0.9.0` (webpack 5, Babel 8 / `@babel/core` 8.1,
  babel-loader 10, pug, html-webpack-plugin). Bun blocks two postinstall scripts
  (`@parcel/watcher`, one `node ./scripts/postinstall.js`); neither is needed.
- `bun run build` (= `plesk-ext-sdk build`), `bunx plesk-ext-sdk build` and
  `bunx --bun plesk-ext-sdk build` all work with **no Node.js installed**: the SDK CLI has a
  `#!/usr/bin/env node` shebang and Bun provides its own `node` shim. No workaround, pinning or
  wrapper was necessary (Bun 1.4.4). Cold build about 17 s, warm about 3 s (babel-loader cache in
  `node_modules/.cache`). `bun run dev` = watch mode.
- `extension.config.js`: the four routes (`overview` first = default page, `toolchains`,
  `settings`, `domain`) and a webpack override that disables production source maps.
- Output: `src/htdocs/dist/main.js` (an AMD module, `define(["plesk-ui-library"], ...)`),
  `main.js.LICENSE.txt` and `src/htdocs/index.php`. Both locations are git-ignored; `build.py`
  runs the build (unless `--no-frontend`), checks that both exist and packages them, without
  `src/frontend/` and `*.map`.
- `react`, `react-dom` and `@plesk/ui-library` are webpack **externals**: at runtime they are
  Plesk's own `plesk-ui-library` AMD module (`/ui-library/plesk-ui-library.min.js`, version
  **3.46.5** on Plesk 18.0.82 — the same as in node_modules). That module also exports the React
  API (`useState`, `createRoot`, `flushSync`, ...). `react-router-dom` 7, `prop-types` and `qs`
  are bundled into `main.js`.
- Babel: preset-env (no targets: ES5 output, no polyfills), preset-react, class properties, and
  JSX with the **classic runtime and pragma `createElement`**: every file that contains JSX must
  `import { createElement } from 'react'`. Plain JS, no TypeScript (DESIGN section 1).
- Module resolution includes `src/frontend`, so route components are referenced by file name.
- Everything the SDK exports: `export * from '@plesk/ui-library'` plus `Component`,
  `createElement`, `PropTypes`, `RouterLink`, `ServerForm`, `ServerList`, `withConfig`,
  `withStatusMessages`, `withRouter`. The SDK's own `api`/`withApi` are **not** exported; use
  `src/frontend/lib/api.js`.

## 3. The generated index.php

`plesk-ext-sdk build` renders `lib/templates/index.pug` of the SDK into `src/htdocs/index.php`
(never edit it; to change it, override the HtmlWebpackPlugin template in `extension.config.js`):

- It defines **`IndexController`** itself. Therefore `plib/controllers/IndexController.php`
  must not exist (class redeclaration).
  - `indexAction()`: `redirect('/overview')` (the first route), so `index.php` alone opens the
    overview.
  - `viewAction()`: no view script; echoes `<div id="runway"></div>` and
    `require(['/modules/runway//dist/main.js'], main => main.default({moduleId: 'runway',
    baseUrl: '/modules/runway/index.php', locale: <pm_Locale::getSection('app')>}))`. Plesk
    wraps it in the normal panel layout (navigation, breadcrumbs, page header).
- It registers the action helpers `PleskExt_SDK_ServerList` / `PleskExt_SDK_ServerForm`
  (`$this->_helper->serverList(...)`, `$this->_helper->serverForm(...)` in any controller).
- Routes: `'Default' => ':controller/:action'` plus one route per frontend path
  (`/overview`, `/toolchains`, `/settings`, `/domain` → `index/view`). Zend's default module
  route (`:controller/:action/*`) still applies to everything else; this is how
  `index.php/api/app/save` reaches `ApiController::appAction()` (the extra segment becomes a
  request parameter, `appAction()` reads it from the path info).
- It does not call `pm_Context::init()` (Plesk sets the module context for `/modules/runway/`).
- The React app (SDK `App`) wraps every route component in `ConfigProvider` (baseUrl),
  `LocaleProvider` (the `app` locale section), the SDK `ApiProvider`, `BrowserRouter` with
  `basename = baseUrl`, and `StatusMessages` (a `Toaster`, reachable via
  `withStatusMessages`). Route components receive the props `moduleId` and `baseUrl`.
- Page titles: the SDK `Page` component sets the Plesk page header to the translation
  `<Component>.title` (fallback: `title` of the route). The `app` section arrives flattened
  (`"Overview.title"`, `"Overview.state.running"`); nested PHP arrays are fine.
- URLs: `/modules/runway/index.php/overview|toolchains|settings`,
  `/modules/runway/index.php/domain?site_id=<id>` (the CustomButtons hook links
  `index.php/overview` from the admin navigation and `index.php/domain` with `contextParams`
  from the domain's Dev Tools, which appends `?dom_id=<sub>&site_id=<id>`). Client-side
  navigation uses react-router (`<Link to="/domain?site_id=1">`); full reloads hit the PHP
  route. Read query parameters with `queryParam('site_id')` (lib/hooks.js).

## 4. API client usage pattern

```js
import { createElement, useState } from 'react';
import { Button, Form, FormFieldText, Translate } from '@plesk/plesk-ext-sdk';
import { formErrors } from './lib/api';
import { queryParam, useApi, useApiData, usePolling } from './lib/hooks';
import ErrorAlert from './components/ErrorAlert';

const Example = ({ baseUrl }) => {
    const api = useApi(baseUrl);                                  // bound to /modules/runway/index.php
    const siteId = queryParam('site_id');
    const page = useApiData(() => api.get('app', { site_id: siteId }), [api, siteId]);
    const [error, setError] = useState(null);
    const poke = usePolling(() => page.reload(), 6000, true);     // pauses while the tab is hidden
    const save = values => api.post('app/save', { ...values, site_id: siteId })
        .then(result => { /* result = response.data */ page.reload(); }, setError);
    return (
        <div>
            <ErrorAlert error={page.error || (error && !error.fieldErrors ? error : null)} />
            <Form values={page.data ? page.data.config : {}} errors={formErrors(error)} onSubmit={save} />
        </div>
    );
};
```

- `api.get(path, query)` / `api.post(path, body, query)` resolve with `response.data` of
  `{"status":"success","data":...}` and reject with an `ApiError`:
  `error.message` (first message), `error.messages` (all), `error.fieldErrors`
  (`{field: ['msg']}` for validation errors, else `null`), `error.status` (HTTP status).
- Every request sends `X-Forgery-Protection-Token` (from `<meta id="forgery_protection_token">`)
  and `X-Requested-With`; POST bodies are JSON. Plesk rejects a POST without a valid token
  **before** the controller runs and answers `{"message": "ERROR: ... Session token has expired ..."}`;
  the client turns that into an ApiError too. Non-JSON answers (expired session, PHP fatal)
  become "Unexpected response from the server (HTTP n)".
- `formErrors(error)` converts field errors to the ui-library `Form` format
  (`{field: {e0: 'msg'}}`).
- `usePolling(tick, ms, active)` returns `poke()`: call it on user actions so polling also runs
  for 2 minutes while the tab is hidden (DESIGN section 8).

## 5. Server side (PHP)

- `ApiController::respond(callable)` wraps every action: return an array → `success`;
  throw `Modules_Runway_ValidationException(['field' => ['msg']])` → errors keyed by field;
  throw `Modules_Runway_Exception`/`pm_Exception` → `{"status":"error","errors":["msg"]}`;
  anything else is logged to panel.log and answered with the generic `errorInternal`.
  Responses always use HTTP 200 (SDK convention).
- Helpers inside the controller: `body()` (JSON body, falls back to form-encoded POST data),
  `requirePost()`, `appModel()` (domain from `site_id` in the body or the query string through
  `Modules_Runway_Access::domainFromRequest($request, $body)`), `appSubAction()`.
- New top-level action `foo-bar` → method `fooBarAction()` (URL `api/foo-bar`). New domain
  action → add a `case` in `appAction()` (URL `api/app/<name>`).
- `Modules_Runway_App::update(array $values, $isAdmin)` is a **partial update**: missing keys
  keep their stored value; `env` changes only when sent (send nothing when `api/app` returned
  `env: null`, i.e. the stored variables could not be loaded). Booleans accept
  `true/false/1/0/"1"/"0"/"on"/"off"`. `staticPaths` accepts an array or newline/comma text.
  `mode: worker` ⇔ `listen: none` are normalised to each other.
- `Modules_Runway_App::$notImplemented` (`listen: none`, `mode: path|worker`) is the gate that
  answers `"<value>" is not supported yet` keyed by field. **Phase 3a/3b remove the entries**
  once the helper and WebConfig support them.
- `mountPath`, `staticPaths`, `healthPath` and `mode` are validated, stored in `runwayApp`
  and sent to the helper as `mount_path`, `static_paths`, `health_path`, `mode` — the Phase 2
  helper ignores them. `App::proxyTarget()` already returns `mode`, `mountPath` and
  `staticPaths` next to `port`/`socket` (returns `null` for workers); `WebConfig` ignores them
  so far (3b).
- `Modules_Runway_Runtime::all()` = helper `runtimes` (cached per request; minimal go/rust/binary
  fallback when the helper fails). Runtime validation and toolchain syntax checks
  (`isValidVersion`, using `version_re`) are driven by it, so new helper adapters appear in
  the API without PHP changes.
- Settings: `Modules_Runway_Settings::update()` validates against `ranges()`;
  `maxAppsPerSubscription` (0..10000, default 0) is stored but **not enforced** yet (3b).
- `api/overview` lists every domain with hosting the user may manage (`configured` false =
  no app), `state` ∈ `notConfigured|disabled|suspended|running|starting|stopping|failed|stopped`,
  `url` = `http://<domain>/` (site URL; the panel page is `/domain?site_id=<domainId>`), plus
  `errors` (helper failures; the list still renders).
- `api/toolchains` supports `?runtime=<key>` (one runtime), `?available=0` (skip the release
  lists: fast refresh after a job) and `?force=1` (bypass the 6 h release cache).
- `api/job` accepts `admin` and `deploy-<id>` (admin only); domain users get the deploy job
  through `api/app/status` (`deploy`) and `api/app/logs?kind=deploy`.
- `api/app` returns the DESIGN fields plus `buildDeps` (for the "no C compiler" warning) and
  `pageError` (helper failure; the rest of the page data is still returned).
- `api/app/sample` and `api/app/fetch` answer `errorFeatureNotImplemented` (3a + 3b).

## 6. Helper changes beyond the rename (contract of DESIGN section 7)

- `runtimes` → `{runtimes: [meta...]}` from the static `RUNTIME_META` table (go, rust,
  binary) with exactly the DESIGN fields. `RUNTIME_KEYS` drives `validate_app`.
- `toolchains` → `{runtimes: {key: {installed: [{id, label, path[, version]}], in_use: {id: [domains]}}},
  build_deps, job}`.
- `releases {runtime, force}` → `{runtime, available: [{id, label}], error}` (network errors
  never fail the command).
- `toolchain-install|-update|-remove {runtime, version}` (the base used `kind`).
- `app-page {domain_id, sysuser, app_root, runtime}` → also `defaults: {key: {build_cmd, start_cmd}}`
  (project-aware: Rust uses the Cargo package name), `toolchains: {key: [installed...]}` and
  `build_deps`.
- `RESERVED_ENV` now also contains `RUNWAY_SOCKET` and `RUNWAY_LISTEN` (same list as
  `Modules_Runway_App::$reservedEnv`; keep both in sync).
- Everything else (validation, units, env file, jobs, deploy, listener checks, security
  invariants) is unchanged from the base apart from names.

Phase 3a replaces `RUNTIME_META`, `toolchain_list()`, `runtime_defaults()` and the go/rust
branches of the toolchain commands with the adapter registry, keeping these output shapes.

## 8. Things to know / pitfalls

- **Customer access is untested**: the trial license of the container allows no customer
  accounts (`clients` limit 0). The generated `IndexController` and `ApiController` do not set
  `$_accessLevel` (the base's `DomainController` did not either and served customers); every
  API action checks access itself.
- In the container nginx listens on `172.17.0.2`, not `127.0.0.1`; `gotest.local` redirects
  HTTP to HTTPS. Use `curl -k --resolve gotest.local:443:172.17.0.2 https://gotest.local/`.
- Git Bash on Windows: `MSYS_NO_PATHCONV=1` only for `docker` commands; exported globally it
  breaks POSIX paths given to native tools (curl cookie jars). `python3` may be the Microsoft
  Store stub: probe it (see `tests/api-smoke.sh`).
- pyflakes is not installed in the container; lint the helper locally (`python -m pyflakes`).
- `check_locales.py` finds frontend keys in `content="..."`, `content={'...'}` and
  `translate('...')`/`lmsg('...')`/`t('...')`; keys built with template literals must be
  listed in `DYNAMIC_APP`. Both locales must have identical key sets and placeholders.
- The four pages are deliberately rough placeholders (raw JSON sections, no dialogs, no tabs):
  Phase 3c replaces them. Keep the component file names (they are route ids and title keys).
- The extension version is still 1.0.0-1; `plesk bin extension --upgrade` with the same
  version works for development.
- `meta.xml` contains `<url>https://github.com/Taiizor/plesk-ext-runway</url>` (DESIGN repo name;
  the owner is an assumption — 3d should confirm).
